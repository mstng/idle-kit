# idle-kit — 放置育成ゲームの型

「そだつ」という小さな放置育成ゲーム。遊べる完成品というより、**次にちゃんとした放置ゲーを作るときの下敷き**として書いた参考実装です。

## 動かす

```bash
cd idle-kit
npm test          # コアロジックのテスト（20件）
npm run serve     # http://localhost:8765 で開く
```

依存パッケージはゼロ。テストは Node 標準の `node:test`、画面は素の HTML + ES モジュールです。

> ES モジュールを使っているため、`index.html` をファイルとしてダブルクリックしても動きません。必ず `npm run serve` 経由で開いてください。
>
> `tools/serve.js` はキャッシュ無効のヘッダを返します。ふつうの静的サーバーだと
> ブラウザが古い ES モジュールを使い続け、リロードしても直らない状態にはまります
> （import 先まで個別にキャッシュされるため、実際に開発中これで足を取られました）。

## ファイル構成

| ファイル | 責務 |
|---------|------|
| `src/bignum.js` | 巨大数（仮数＋指数）。桁あふれ対策。ゲームのことは何も知らない |
| `src/game.js` | **ゲームのルール全部**。純粋関数のみ。DOM も localStorage も時計も触らない |
| `src/ui.js` | 画面の描画・保存・ループ。ルールは一切書かない |
| `tools/serve.js` | 開発用サーバー。キャッシュを無効にするためだけに自前で用意している |
| `test/bignum.test.js` | 巨大数のテスト |
| `test/game.test.js` | コアロジックのテスト |
| `index.html` | 見た目 |

この分け方が一番大事な設計判断です。ルールが純粋関数に閉じていると、
テストが素直に書けるうえに、**画面を作り替えてもゲームが壊れません**。
UI を React に載せ替えるのも `ui.js` を捨てるだけで済みます。

## 放置ゲーを支える4つの型

### 1. 実時間ベースの tick — `tick(state, elapsedMs)`

増加量は**経過ミリ秒**から計算します。フレーム数で数えると、
端末の性能やリフレッシュレートでゲームの進行速度が変わってしまいます。
放置ゲーは時計が主役なので、ここを間違えると全部が狂います。

`ui.js` の更新間隔（100ms）を変えても進行速度が変わらないのは、この設計のおかげです。

### 2. オフライン進行 — `advanceTo(state, now)`

このジャンルの存在理由。見ていない間も進むから「放置」ゲーです。

**オンライン進行とオフライン進行を同じ関数に通しているのが肝**です。
別々に実装すると必ず計算がズレます（このジャンルで最頻出のバグ）。
`advanceTo` は経過時間を見て、自分で「これはオフラインだった」と判断します。

守っている境界は3つ：

| 守り | 値 | 理由 |
|-----|---|------|
| 上限 | 8時間 | 1週間放置で無限に強くなるのを防ぐ |
| 効率 | 50% | 100%にすると戻ってくる理由がなくなる |
| 時計の巻き戻り | 増加なし | 端末の時刻をいじられても所持量が壊れない |

### 3. 指数コスト曲線 — `upgradeCost(id, level)`

`コスト = baseCost × growth^level`（指数）に対して、`効果 = effect × level`（線形）。

コストだけを指数にすると、レベルを上げるほど次の1レベルが遠くなり、
プレイヤーは**永久に「あと少しで買える」状態**に置かれます。
放置ゲーの推進力はほぼこの式だけで作られています。

`growth` は 1.15〜1.25 あたりが定番。上げるほど「詰まり」が早く来ます。

### 4. 壊れないセーブ — `serialize` / `deserialize` / `migrate`

放置ゲーはセーブが壊れた瞬間に終わります。`deserialize` は
壊れたJSON・未来のバージョン・項目の欠損のどれが来ても例外を投げず、
読める範囲だけ生かして初期値で埋めます。

古い形式は捨てずに `migrate` で引き上げます。バージョンを飛ばさず
**1段ずつ**上げるのがポイントで、こうすると移行のテストが各段で書けます。

```js
const MIGRATIONS = {
  1: (data) => ({ ...data, version: 2, megumi: 0, ... }),
};
```

保存キーにバージョンを含めない（`idle-kit:save` のまま固定する）のも意図的です。
キーを変えると古いセーブが「見つからない＝進行が消えた」ことになります。
形式の変更はキーではなくデータ内の `version` で吸収します。

### 5. プレステージ（転生） — `prestige(state, now)`

放置ゲーが数ヶ月遊ばれる理由は、ほぼこれ一点です。

進行をすべて捨てる代わりに、永続通貨「めぐみ」を受け取ります。
めぐみは生産量に永続倍率をかけるので、次の周回は前回より速く同じ地点に到達します。

重要なのは、これが**プレイヤー自身が決断する損失**だということ。
ゲームが取り上げるのではなく、プレイヤーが「いま手放すか、もう少し伸ばすか」を選ぶ。
この判断そのものが遊びになっています。だから UI では、失うものを確認ダイアログで明示しています。

設計上の勘所は3つ：

| 判断 | 内容 | 理由 |
|-----|------|------|
| 取得量は平方根 | `floor(sqrt(累計 / 10万))` | 線形だと転生のたびに報酬が爆発してゲームが即終わる。平方根なら「2倍もらうには4倍稼ぐ」となり周回間隔が自然に伸びる |
| 倍率は掛け算 | `段階倍率 × めぐみ倍率` | 足し算だと周回するほど旨みが薄れる。掛けることで再成長が毎回速くなる |
| 記録は残す | `lifetimeEarned` は転生でも減らない | 全部消えると喪失感だけが残る。積み上がる数字を1つ残すと「進んでいる」感覚が保てる |

到達していない間も「あと◯◯ためると めぐみを◯こ うけとれます」を常に表示しています。
放置ゲーは**次の目標が常に見えていること**が生命線です。

### 6. 永続通貨の使い道 — `MEGUMI_UPGRADES`

めぐみの使い道が「生産量の倍率」しかないと、転生はただ数字が増えるだけの作業になります。
使い道を複数用意して初めて「今回のめぐみを何に使うか」という**毎周の判断**が生まれます。

意図的に効き方の種類を変えてあります。同じ「強くなる」でも軸が違うほど選択が面白くなります。

| 名前 | 効果 | 軸 |
|-----|------|---|
| はじまりのめ | 転生後、おひさまを持って再開 | 立ち上がりの速さ |
| ねむりのちから | オフライン効率 +10%（上限100%） | 生活リズム |
| てのひら | 手動の獲得量 ×10 | 序盤の手触り |

ここで効いてくるのが**手持ちと累計を分ける**設計です。

```js
megumi:        // 手持ち。買い物で減る
megumiEarned:  // 累計。生産倍率はこちらで決まる
```

同じ数字を使い回すと、めぐみを使った瞬間に生産量が落ちます。
そうなるとプレイヤーは「使わないのが最適」と学習し、せっかくの使い道が死にます。
`light` と `totalEarned` を分けているのとまったく同じ理屈です。

### 7. 数値のインフレ対策 — `src/bignum.js`

放置ゲーで必ず来る壁。JavaScript の `Number` は**約 1e308 を超えた瞬間に `Infinity`** になり、
そこから先は足しても掛けても `Infinity` のまま。転生を重ねたプレイヤーのゲームが静かに壊れます。

```js
1e308 * 100 === Infinity   // 素の Number
pow(2, 5000).e === 1505    // Big なら続けられる
```

対策は「巨大な数をそのまま持たない」こと。`m × 10^e` の形（仮数と指数）で保持すれば、
指数側が `Number` なので実質 `10^(1.7e308)` まで扱えます。
代わりに精度は有効数字16桁ぶんだけになりますが、放置ゲーでは十分です
（1兆の山に1を足した結果が正確である必要はない）。

実装で気をつけた点：

- **正規化を1か所に集約** — すべての演算の出口で `1 <= |m| < 10` に直す。
  桁ずらしを while ループでやると桁が大きいとき遅いので `log10` で一発で求める
- **桁が離れすぎた足し算は捨てる** — `1e100 + 1` は有効数字に現れない。
  無理に計算しないことが精度を守る
- **小さい範囲は素の計算を使う** — `pow` は `Number` で正確に表せる範囲なら直接計算する。
  `log10` 経由だと `5^2` が `25.000000000000004` になり、切り上げたコストが 50 ではなく 51 になる
- **壊れた値を伝播させない** — `NaN` や `Infinity` が入ってきたら 0 として扱う。
  1か所の異常が全部の数字を `NaN` にする事故を防ぐ
- **`Number` に戻す瞬間に誤差が復活する** — `1.92×10^2` は `Number` にすると `192.00000000000003`。
  そのまま切り上げると 193 になる。`floor`/`ceil` は信用できる15桁で丸めてから整数化する

### 8. オートバイヤー — `runAutoBuyer(state)`

後半は「買えるようになった瞬間に買う」だけの作業が延々と続きます。
それを肩代わりして、ようやく**本当に放置していられるゲーム**になります。

解禁はめぐみで買う形にして、`じどうのて` Lv.N で `UPGRADES` の先頭からN種類が対象になります。

判断が要るのは3点です。

| 論点 | 判断 | 理由 |
|-----|------|------|
| 何を買うか | 効果 ÷ コストが最良のもの | 安い順だと効率の悪いものを買い続けて成長が鈍る。倍率は全アップグレードに等しく掛かるので、順位はこの比だけで決まる |
| 暴走をどう防ぐか | 1回につき50件で打ち切り | 8時間放置から戻ると数百回ぶん買えてしまう。打ち切っても残りは次のtickで買われるので損はしない |
| どこで走らせるか | `advanceTo` の中 | 別経路にすると「放置して戻ったらひかりが大量に余っている」状態になる。入口一本化の原則を崩さない |

なお `advanceTo` の中で一括購入するため、実際に放置中ずっと買い続けた場合よりは
結果が控えめになります（本来は途中で買った分がさらに稼ぐため）。
厳密に再現するには時間を刻んでシミュレートする必要があり、そこは割り切っています。

**上限のあるアップグレードは買えないようにする**のも忘れずに。
`ねむりのちから` は効率100%で頭打ちなので `maxLevel` を設けています。
効果のない買い物ができる状態を放置すると、プレイヤーに永続通貨を無駄づかいさせてしまいます。

## 数字をいじる場所

チューニング用の定数は `src/game.js` の先頭にすべて集約してあります。
まずはこのあたりを触ると手触りが変わります。

| 定数 | いまの値 | 上げると |
|------|---------|---------|
| `OFFLINE_EFFICIENCY` | 0.5 | 放置の旨みが増す／復帰の動機は薄れる |
| `OFFLINE_CAP_MS` | 8時間 | 長期放置が報われる／復帰頻度は落ちる |
| `STAGE_BONUS_PER_LEVEL` | 0.25 | 進化の達成感が強くなる／インフレが早い |
| `UPGRADES[].growth` | 1.15〜1.25 | 進行が遅く重くなる |
| `MEGUMI_DIVISOR` | 10万 | 転生の間隔が長くなる |
| `MEGUMI_BONUS` | 0.1 | 1周ごとの伸びが大きくなる／インフレが早い |
| `MEGUMI_UPGRADES[].growth` | 4〜8 | めぐみアップグレードが重くなり、何を買うか選ばされる |
| `AUTO_BUY_MAX_PER_TICK` | 50 | 復帰時の処理が重くなる。下げても取りこぼしはない |

## ここから「ちゃんとしたもの」に育てるなら

この土台に足すと効くもの、優先度順：

1. ~~**プレステージ（転生）**~~ — 実装済み
2. ~~**転生でしか買えないアップグレード**~~ — 実装済み（`MEGUMI_UPGRADES`）
3. ~~**数値のインフレ対応**~~ — 実装済み（`src/bignum.js`）
4. ~~**オートバイヤー**~~ — 実装済み（`runAutoBuyer`）
5. **実績・アンロック** — プレイヤーに短期の目標を配り続ける。放置ゲーの離脱は「次にやることが見えない瞬間」に起きる
6. **2周目以降の解禁要素** — 転生回数に応じて新しいアップグレードや段階を開放し、周回の景色を変える
7. **オフライン進行の精密化** — いまは一括計算。時間を刻んでシミュレートすれば、放置中の自動購入まで正確に再現できる
8. **サーバー保存とチート対策** — localStorage は書き換え放題。ランキングを付けるなら進行をサーバーで検証する

## 設計上の注意点

- `advanceTo` に渡す `now` は必ず呼び出し側から渡す。`game.js` の中で `Date.now()` を呼ぶと時刻を固定したテストが書けなくなる
- 進化の判定は所持量ではなく**累計獲得量**（`totalEarned`）で行う。所持量で判定すると買い物した瞬間に退化する
- 状態は毎回新しいオブジェクトを返す（イミュータブル）。テストで「呼び出し元が書き換わっていないこと」を検証している
- 「所持」と「累計」は必ず分けて持つ。`light`/`totalEarned` も `megumi`/`megumiEarned` も同じ理由（使ったら弱くなる、を避ける）
- 数値は `Big` で持ち、`toNumber()` は表示と小さい値の比較にだけ使う。大きい値に使うと `Infinity` になって台無しになる
